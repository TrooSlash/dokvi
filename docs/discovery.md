# Как находить пользователей Dokvi

[Подготовка публикации](releasing.md) · [Тексты анонсов](launch-posts.md)

Цель первого выпуска: человек находит Dokvi, понимает, что это программа для `.md` в Windows, скачивает EXE и открывает свой документ. Переходы и загрузки нужно измерить после публикации. Сейчас данных для прогноза аудитории нет.

## Что заполнить на GitHub

Название репозитория оставьте `Dokvi`. В **About → Description** вставьте:

```text
Markdown reader and editor for Windows with live preview, tabs, draft recovery, and PDF export. Free and open source. English / Russian.
```

Это описание для GitHub. Оно не задаёт гарантированный текст сниппета Google.

В **About → Topics** добавьте темы ниже, каждую отдельно:

```text
markdown
markdown-reader
markdown-viewer
markdown-editor
windows
desktop-app
live-preview
markdown-to-pdf
mermaid
latex
webview2
```

Темы помогают искать связанные проекты внутри GitHub. Они описывают назначение и реализованные функции Dokvi. [Правила GitHub для topics](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/classifying-your-repository-with-topics).

Порядок публикации:

- [ ] Загрузить исходники с английским `README.md`, русским `docs/README.ru.md` и папкой изображений.
- [ ] Заполнить About и Topics.
- [ ] Создать Release `v3.0.0` и прикрепить EXE, руководство, MIT и SHA256 по [инструкции](releasing.md).
- [ ] Проверить скачивание EXE и обе версии README без входа в GitHub.
- [ ] Закрепить репозиторий в своём профиле GitHub.
- [ ] Проверить карточку ссылки в месте будущего анонса. При необходимости выбрать существующий снимок `docs/images/editor.png` в Settings → Social preview. [Настройка карточки GitHub](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/customizing-your-repositorys-social-media-preview).

Ссылки README ведут на общий раздел Releases: они сохранят смысл после следующей версии. До загрузки EXE анонсы откладываются.

## По каким запросам описывать проект

Это гипотезы о намерениях пользователей, а не исследование частотности или обещание позиций:

| Намерение | Английский запрос | Русский запрос | Где дан ответ |
| --- | --- | --- | --- |
| Открыть документ | open md file Windows | чем открыть md файл Windows | Раздел запуска README |
| Читать с форматированием | Markdown reader for Windows | читалка Markdown для Windows | Название, введение и снимок |
| Править исходник | Markdown editor with live preview | редактор Markdown с предпросмотром | Возможности и снимок редактора |
| Получить PDF | Markdown to PDF Windows | Markdown в PDF | [Инструкция экспорта](markdown-to-pdf.md) |
| Найти программу по имени | Dokvi Markdown editor | Dokvi редактор Markdown | Название репозитория и README |

На странице нужны ответы на эти задачи обычным языком. Списки повторяющихся ключевых слов и скрытый текст не добавляются. Google рекомендует полезный текст, ясные заголовки и ссылки; индексация и рост позиций не гарантируются. [Руководство Google](https://developers.google.com/search/docs/fundamentals/seo-starter-guide).

## Первые публикации

Сначала используйте [короткий анонс на русском](launch-posts.md#русский-анонс) в своём канале или одном сообществе Windows, где разрешено показывать собственные программы. Приложите реальный снимок редактора и ссылку на репозиторий. После публикации выделите время на ответы и ошибки первого запуска.

Для англоязычной технической аудитории можно попробовать **Show HN** после появления работающей загрузки. В [английском черновике](launch-posts.md#english-announcement) есть название и описание. Перед отправкой дополните его своей реальной историей разработки. Правила площадки требуют, чтобы проект можно было попробовать, а автор был готов его обсуждать; просить голоса нельзя. [Show HN Guidelines](https://news.ycombinator.com/showhn.html).

Не публикуйте одинаковый текст сразу в десятках сообществ. Выберите место, где люди действительно открывают Markdown-документы, и отвечайте по существу. Формулировки «самый быстрый» и «работает на любом ПК» потребовали бы сравнительных замеров на указанном оборудовании; в текущих материалах таких заявлений нет.

## План на первый месяц

| Когда | Действие | Как оценить результат |
| --- | --- | --- |
| Перед анонсом | Опубликовать репозиторий и Release, проверить путь от README до открытого файла | EXE доступен без авторизации; требования видны до загрузки |
| Первая неделя | Один русский и один английский анонс, разнесённые по времени | Посещения, загрузки EXE, содержательные ответы, ошибки запуска |
| Вторая неделя | Исправить повторяющиеся проблемы; уточнить непонятные шаги запуска | Повторяются ли те же вопросы после правок |
| Третья–четвёртая недели | Написать разбор конкретной задачи, например экспорта формул и таблиц в PDF; поделиться там, где это уместно | Переходы после публикации и новые вопросы по задаче |

Это порядок работы, а не прогноз количества пользователей. Если посетители приходят, но не находят EXE, сначала улучшайте загрузку и требования. Если скачивают, но не могут запустить, сначала исправляйте запуск.

## Что измерять

Раз в неделю сохраняйте **Insights → Traffic**: посетителей, просмотры и доступные источники переходов. GitHub показывает посетителей за последние 14 дней, поэтому для истории нужна отдельная запись. [Документация Traffic](https://docs.github.com/en/repositories/viewing-activity-and-data-for-your-repository/viewing-traffic-to-a-repository).

Количество скачиваний EXE доступно в поле `download_count` конкретного release asset через [GitHub Releases API](https://docs.github.com/en/rest/releases/assets#get-a-release-asset). Записывайте разницу между двумя датами для одного файла. Это счётчик скачиваний, а не число установок или активных пользователей. Звёзды тоже не измеряют использование программы.

## Отдельный сайт позднее

Если нужен самостоятельный адрес в Google и Яндексе, следующий этап — небольшая страница проекта на управляемом сайте: английская и русская версии, настоящий снимок, требования и ссылка на GitHub Releases. Там можно настроить собственные заголовки, описания и инструменты вебмастера после подтверждения прав. Вставка `meta`-тегов в README не даёт управления HTML-заголовком страницы GitHub.

Пока сайт и платная реклама не создавались. Сначала стоит проверить, что опубликованный Release успешно запускают первые пользователи, и собрать их вопросы.
